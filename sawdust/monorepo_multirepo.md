## 总结

选型先看**变更是否需要一起发生**，而不是单看仓库数量：

- **Monorepo**：多个应用或包放在同一仓库，适合依赖紧密、频繁联动、需要跨端复用的项目。
- **Multirepo**：应用或包分散在不同仓库，适合协作边界清晰、独立演进、通过稳定契约交互的项目。

一句话：**频繁一起改，优先考虑 Monorepo；更需要独立演进与隔离，优先考虑 Multirepo。**

## 怎么选

| 维度 | Monorepo | Multirepo |
| ---- | -------- | --------- |
| 变更关系 | 经常需要跨应用、跨包联动 | 多数改动可在单仓内完成 |
| 团队协作 | 同一团队或紧密协作团队 | 团队职责、权限与交付边界更独立 |
| 依赖消费 | 可通过 workspace 使用仓库内的本地包 | 常通过包仓库与版本号消费发布产物 |
| 变更提交 | 可用同一个提交 / PR 完成联动修改 | 通常需要协调多个仓库与依赖升级 |
| 工程成本 | 需要管理依赖图、任务编排与 CI 范围 | 需要管理发版、版本兼容与跨仓协同 |
| 典型场景 | 多端应用、共享业务逻辑、配套组件库 | 独立业务应用、跨团队 SDK、独立 CLI |

仓库组织和发布方式不是一回事：**Monorepo 也可以独立发布各应用和包；Multirepo 也不意味着项目之间没有依赖。**

## 场景：Web 与客户端 WebView 共享能力

一个项目同时维护 Web 端与客户端内的 WebView 页面：

- **共性**：共享设计变量（Design Tokens）、基础 UI、业务计算逻辑与服务端接口契约。
- **差异**：Web 运行在标准浏览器中，客户端页面运行在原生容器中，通过 JSBridge 使用宿主能力。

如果两端经常联动修改，Monorepo 可以缩短「改公共包 → 发版 → 应用升级 → 联调」的反馈链路。

### 1. 按职责拆包，避免「上帝包」

不要把 UI、业务、平台判断全部塞进一个 `sdk`。可以先按以下边界组织，再根据规模调整：

```text
apps/
  web/                 # 浏览器入口
  client-webview/       # 客户端 WebView 页面入口，不是原生壳工程
packages/
  ui/                  # 设计变量与纯展示组件
  core/                # 接口契约、业务状态与计算逻辑
  adapter/             # 平台能力接口与适配实现
```

边界重点：

- `ui` 不耦合具体宿主能力。
- `core` 保持纯 TypeScript，不直接依赖 DOM 或 JSBridge。
- 平台能力通过接口注入，避免业务逻辑里散落 `if (isWebView)`。

例如，业务只依赖统一的存储接口：Web 端注入 `localStorage` 驱动，客户端注入通过 JSBridge 调用原生存储的驱动。两者同步 / 异步行为不同，接口设计时也要统一约定。

拆包的目的是明确职责，不是越细越好；每个包仍有配置、测试和维护成本。

### 2. 在应用入口装配平台差异

`apps/web` 与 `apps/client-webview` 各自负责路由、启动配置、平台驱动注入和特有功能，公共能力留在 `packages/*`。

使用支持 `workspace:` 协议的包管理器时，同仓依赖可以声明为 `workspace:*`，明确要求解析到工作区内的包。

注意：**本地包依赖不等于自动直引源码。** 实际消费源码还是构建产物，由包的 `exports`、构建配置和应用工具链决定。若依赖产物，需要配置构建顺序或 watch，才能保证本地联调及时更新。

### 3. 用原子变更完成跨端联动

例如接口契约发生变化：

```text
更新 packages/core 中的契约
  → 对受影响的应用执行类型检查与测试
  → 在同一个提交 / PR 中修复两端调用
  → 合并后按各应用节奏部署
```

类型检查可以发现静态类型层面的不兼容，但前提是契约定义准确且检查覆盖调用方；它不能替代运行时接口校验和集成验证。

**原子提交不等于原子部署。** 两端上线时间、服务端版本和用户设备上的原生能力仍可能不同，兼容策略不能省略。

### 4. 构建与发布分别管理

可用 Turborepo / Nx 等工具，根据依赖图组织任务、复用缓存，只执行受影响的检查与构建。公共包变化时，也要覆盖它的消费者，而不只是检查改动目录。

| 交付对象 | 常见方式 | 需要注意 |
| -------- | -------- | -------- |
| Web 静态资源 | 构建后部署到 CDN / 静态服务器 | HTML 与带哈希资源分别配置缓存，避免新旧资源错配；已打开页面不一定立即更新 |
| 客户端 WebView 资源 | 随原生 App 发版、离线包动态下发，或加载远程页面 | 资源版本与原生壳可能不同步，需要能力检测、兼容约定与明确的降级反馈 |

客户端不能假设所有用户都已升级到最新 App。调用 JSBridge 前应检查能力是否存在；缺失时按约定降级，无法继续的关键流程要明确提示。

## 公共包什么时候需要发版

- **同仓且需要同步演进**：优先使用 workspace 本地依赖，减少不必要的发版与升级步骤。
- **供外部团队或跨仓项目消费**：通常需要发布到 npm 私有源等包仓库，并维护语义化版本（SemVer）、变更说明与兼容约定；可用 Changesets 管理版本和发布流程。
- **同仓但需要验证发布产物或锁定稳定版本**：也可以按需走版本化消费，但要明确这是交付要求，而不是默认增加一轮发版链路。

## 记法

> 仓库边界看协作与变更关系，包边界看职责，应用入口负责平台装配，发布边界看交付节奏。Monorepo 降低联动成本，但不会自动解决构建、部署和运行时兼容问题。
