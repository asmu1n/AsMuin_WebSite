## Monorepo vs Multirepo 选型与工程实战笔记

### 一、选型思考与使用场景

- **Monorepo**：更适合**高内聚、强依赖关联、需频繁跨端复用**的业务场景。尤其适合同一个团队（或紧密协作团队）闭环管理。依赖通过**工作区软链接（Workspace 协议）**以源码形式实时联动，改动立即可见，支持原子提交，消除了繁琐的发版与版本漂移成本。
- **Multirepo**：更适合**跨团队、弱关联、低频更新**的场景。依赖通过 **npm 私有源 + 语义化版本号（SemVer）** 进行物理隔离，适合独立基建资产管理（如：全局 CLI 脚手架、跨部门通用 SDK、完全独立的大型业务 App）。

---

### 二、工程场景模拟

> **💡 背景**：一个项目需要同时维护 **Web 端** 与 **客户端**（采用 WebView / Hybrid 混合架构）。
>
> - **共性**：UI/UX 存在大量共有资产（Design Tokens、基础 UI 组件），且核心业务计算逻辑、服务端接口完全一致。
> - **异性**：两端运行时环境不同（标准浏览器环境 vs 原生 JSBridge 容器），且在各自宿主上存在平台特有的扩展功能。

---

### 三、基于 Monorepo 的架构落地决策

#### 1. 拆分公共包：警惕“上帝包”，职责按层解耦

不要将所有逻辑塞进一个单一的 `sdk package`，建议按关注点拆分为微型包（在 Monorepo 中创建包的边际成本几乎为 0）：

- `packages/ui`：样式变量（Tailwind / CSS Vars）与纯展示型原子 UI 组件。
- `packages/core`：服务端 API 请求契约、TypeScript 类型定义（DTO）、核心业务状态与计算逻辑（纯 TS 代码，无 UI 和 DOM 依赖）。
- `packages/adapter`：针对宿主环境的**适配器抽象层**（采用依赖反转/IoC 模式）。例如本地存储对外暴露统一接口，不写 `if (isWebView)`，而是由两端在初始化时分别注入驱动（Web 端注入 `LocalStorage` 驱动，客户端注入 `JSBridge -> 原生存储/MMKV` 驱动）。

#### 2. 应用层装配（Apps）

- `apps/web` 与 `apps/client-webview` 作为独立入口工程。
- 两者通过 `workspace:*` 协议直接源码级引用 `packages/*`，仅需在各自的应用层补充特定平台的装配逻辑与驱动注入。

#### 3. 原子协同（Atomic Changes）与即时联调

- 彻底摆脱原先“改基础包 -> 发版 npm -> 应用端升级依赖调试”的漫长链路。
- 当服务端调整接口时，在 `packages/core` 完成契约修改，两个端应用在本地开发时会**即时产生类型报错提示**。可以在同一个 Git Commit / PR 中完成底层到上层的联动修复，保证主干代码时刻处于可用状态。

#### 4. 差异化 CI/CD 构建流水线与版本兼容策略

配合成熟的构建工具（如 Turborepo / Nx）实现**增量构建（Affected Tasks）**与**独立发布**：

- **Web 端构建**：直接构建纯静态资源，推送至 CDN 走协商缓存，部署即全量生效（持续交付，即时热更）。
- **客户端 WebView 构建**：通常打包为 Hybrid 离线资源包（Asset Bundle）随 Native 发版或由离线包系统动态下发。
    - _关键注意点_：**客户端需严格处理版本兼容**。由于部分用户不更新 App，WebView 中调用的 JSBridge 原生能力必须具备**特性检测（Feature Detection）**或优雅降级逻辑，不可假定运行环境全量处于最新状态。

---

### 四、补充与边界原则

- **内部消费原则（Strict Workspace）**：
  同仓内的 Apps 依赖公共 Packages 时，必须强制走 `workspace:*` 源码依赖。**绝对不建议**在 Monorepo 内部通过发版到 npm 绕一圈再固定版本引入，这会主动放弃 Monorepo 的原子协同优势，倒退回版本碎片化。
- **何时才推送到 npm 仓库？**：
  只有当公共 Package 需要提供给**当前 Monorepo 之外的外部团队/跨仓项目**使用时，才引入自动化发版工具（如 Changesets），打 Tag 并推送到公司的 npm 私服（Private Registry）。
