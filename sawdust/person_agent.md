## 总结

人与 Agent 协作，不是把任务交出去，等最后再审批，而是让两条工作线持续推进：

- **Agent 推进任务**：需求分析、技术方案、代码实现与验证。
- **人保持上下文**：复核需求、理解分析依据、评估方案风险、定义验收标准。

一句话：**Agent 执行向前走，人的理解也要同步向前走，不能只在最后接手审批。**

## 按阶段推进

| 阶段 | 人做什么 | Agent 做什么 | 对齐产物 |
| ---- | -------- | ------------ | -------- |
| 需求启动 | 结合仓库上下文整理目标、范围与约束 | 分析需求及现有实现 | 需求清单与待确认问题 |
| 并发复核 | 二次检查遗漏、边界与隐含假设 | 继续分析实现影响 | 补充后的需求与边界 |
| 方向对齐 | 快速通读分析，确认方向后再启动方案设计 | 输出分析结果，按确认方向设计方案 | 已确认的分析结论 |
| 并发深读 | 精读上一轮分析，理解依据与取舍 | 整理技术方案 | 对现状与改动理由的共同理解 |
| 方案评估 | 推演技术路径，识别兼容性与边缘风险 | 解释取舍并修订方案 | 可执行的调整方案 |
| 验收落地 | 明确验收标准，复核结果与证据 | 实现改动并完成验证 | 改动、验证结果与未解决事项 |

这里的「并发」不是跳过确认：**可以并行理解和复核，但进入下一执行阶段前，仍要对齐关键结论。**

## 三个关键动作

### 1. 先快速对齐，再深入理解

Agent 输出需求分析后，先通读，判断目标、范围和方向是否符合预期。

确认方向后，可以让 Agent 开始设计方案；人在这段时间回头精读分析，重点核对：

- 结论依据的是哪些代码、约束或业务规则。
- 哪些是已确认事实，哪些只是待验证假设。
- 是否遗漏异常路径、边界条件或受影响的调用方。

如果深读时发现关键偏差，应及时同步并暂停受影响的工作，不要让错误假设继续向下传递。

### 2. 评估方案，不只看「能不能实现」

方案评估更重要的是判断改动是否可控：

- **影响范围**：改了哪些模块，是否影响现有行为。
- **兼容风险**：是否存在破坏性改动（Breaking Changes），是否需要迁移或降级。
- **边缘逻辑**：异常、空值、并发、失败重试等路径是否被覆盖。
- **实现取舍**：复杂度是否与需求匹配，有没有更简单的路径。

### 3. 实现前明确验收标准

验收不能只写「功能正常」，要转换成可以检查的结果：

| 类型 | 验收重点 |
| ---- | -------- |
| 核心业务逻辑 | 明确输入、预期输出、异常与边界场景，并落实为单元测试 |
| UI / UX | 明确交互链路、关键状态与视觉效果，覆盖加载、空态和错误反馈 |
| 现有行为 | 明确不能改变的行为，检查相关回归场景 |

将标准交给 Agent 后，由其完成实现与闭环验证；人根据实际改动和验证证据复核，而不是只接受一句「已完成」。

## 记法

> 启动时讲清需求，等待时复核与深读，方案出来后评估风险，实现前定义验收，完成后核对证据。让执行与理解保持双轨同步。
