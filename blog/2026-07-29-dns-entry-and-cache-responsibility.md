浏览器地址栏里是 `https://www.example.com/docs/intro`，并不等于数据包会直连「这台名叫 example 的源站机器」。

更准确地说，一次网页访问至少要拆成三层：

1. **名字**：域名如何被解析  
2. **入口**：TCP/TLS 真正先连上谁  
3. **内容与缓存**：谁生成响应，中间谁还可以存一份副本  

DNS、CDN、静态托管、反向代理，往往分别占据其中一层。混在一起，就会出现「解析明明配了，页面却不对」「证书看不懂」「缓存不知道听谁的」这类问题。

下文先讲通用模型，再以 **Cloudflare（DNS/可选代理）+ Netlify（静态托管）** 作为常见示例对照。文中域名均为示意。

<!-- truncate -->

## 1. 核心命题

> **域名写在 URL 里，只保证“用户看见的名字”；不保证“流量第一跳打到谁”，更不保证“文件物理上躺在哪”。**

把下面三个问题分开问，事情会清晰很多：

| 问题 | 典型答案来源 |
| --- | --- |
| 这个名字解析成什么？ | 权威 DNS 区里的记录 |
| 浏览器先和谁握手？ | 解析结果对应的入口（源站 / CDN / 代理） |
| 响应正文从哪来，能不能被中间层复用？ | 源站/托管平台生成；浏览器与 CDN 按头与规则缓存 |

很多人以为链路是：

```text
域名 → 唯一服务器 → 页面
```

现代站点更常见的是：

```text
域名
  → DNS 给出“当前入口”
  → 入口可能是 CDN/代理/托管边缘
  → 必要时再回源到对象存储、应用服务器或构建产物仓库
  → 沿途每一层都可能决定是否缓存
```

---

## 2. 一张通用访问链

以打开一个文档页为例：

```text
浏览器
  │ 1. 解析 URL，取出 host = www.example.com
  ▼
DNS
  │ 2. 查缓存 → 递归解析 → 权威 DNS
  │ 3. 得到 A/AAAA，或 CNAME 后再继续查
  ▼
连接入口
  │ 4. 与解析到的 IP 建连，做 TLS（证书常签给用户看到的域名）
  │ 5. 发送 HTTP 请求，Host/SNI 仍是 www.example.com
  ▼
入口节点（CDN / 托管边缘 / 反向代理 / 源站）
  │ 6. 查边缘缓存；命中则直接返回
  │ 7. 未命中则回源，取 HTML/JS/CSS/图片等
  ▼
浏览器
  │ 8. 再按响应头决定本地是否缓存
  │ 9. 解析 HTML，继续请求其它资源（各自再走类似路径）
```

这里有两个容易反直觉的点：

### 2.1 URL 里的 host，和“连上的机器”可以不是同一家

用户始终请求 `www.example.com`，但 DNS 可以把这个名字指到：

- 自己的云主机
- 静态托管平台边缘
- CDN 任播地址
- 负载均衡 / API 网关

前端代码一般**不必**写成某个机房的临时主机名；对外只暴露稳定业务域名即可。

### 2.2 “入口”和“内容生产者”也可以不是同一家

例如：

- 入口是 CDN，内容在对象存储
- 入口是代理平台，内容在另一云的应用服务
- 入口是托管平台边缘，内容来自最近一次 Git 部署产物

所以排障时不要只问“域名解析对不对”，还要问：

1. 解析是否指向了你以为的那类入口  
2. 该入口是否配置了这个自定义域  
3. 证书在用户路径上由谁终止  
4. 缓存由哪一层决定

## 3. DNS 在这条链里到底做什么

DNS 的工作很单一，但后果很大：

> **把名字翻译成“下一步该去哪”。**

### 3.1 权威 DNS 与递归解析

- **权威 DNS**：域名所有者配置记录的地方，对“正确答案”说了算  
- **递归解析器**：运营商/公共 DNS 等，帮浏览器去问权威并缓存答案  

你在某家 DNS 控制台改记录，改的是权威答案；全球是否马上一致，还受 TTL 与各地缓存影响。

### 3.2 常见记录与访问入口的关系

| 记录 | 直观含义 | 和网页访问的关系 |
| --- | --- | --- |
| `A` / `AAAA` | 名字 → IP | 浏览器最终要连的地址常落成 IP |
| `CNAME` | 名字 → 另一个名字 | 常用于把业务域指到托管/CDN 厂商给出的目标名 |
| `NS` | 这片区交给谁做权威 | 决定你去哪家面板改解析 |
| `TXT` / `MX` 等 | 验证、邮箱等 | 不直接决定网页入口，但常和同一域名共存 |

对自定义域接入托管平台，最常见模式是：

```text
www.example.com
  CNAME → site-name.provider.example
provider.example
  再解析到一组任播/负载 IP
```

根域 `example.com` 受传统 DNS 限制，往往不能随意 CNAME，所以会看到：

- 直接 `A`/`AAAA` 到平台 IP  
- 或 DNS 厂商提供的 CNAME flattening / ALIAS  

心智模型仍是：**让用户看见的名字，最终落到可服务 HTTP 的入口上。**

### 3.3 DNS 配“对了”仍打不开的常见原因

DNS 只完成指路。后面还可能失败在：

- 入口不认这个 Host（平台未绑定自定义域）
- 证书未签发或签错名
- 入口回源到错误上游
- 仅 IPv6/仅 IPv4 不对称
- HSTS / 强制 HTTPS 跳转环
- 本地还在用旧 DNS 缓存

所以「解析已生效」只是整条链路的起点，不是终点。

## 4. 入口层：流量真正先落到哪里

把“入口”定义成：

> 浏览器 TCP/TLS 握手的第一跳服务端。

### 4.1 几种典型入口形态

| 形态 | 浏览器先连谁 | 内容常在哪 |
| --- | --- | --- |
| 源站直出 | 应用服务器 / Nginx | 同一台或后面的应用 |
| 反向代理 | Nginx / API 网关 | 后面多台应用 |
| CDN 代理 | CDN 边缘 | 源站或对象存储 |
| 静态托管平台 | 平台边缘 | 平台上的部署版本 |
| DNS 仅解析到托管，无第二层代理 | 托管边缘 | 同上 |

### 4.2 为什么入口可以“冒充”你的域名

因为 TLS 与 HTTP 都按“用户以为的名字”工作：

- 证书签给 `www.example.com`
- 请求 `Host: www.example.com`
- 入口根据 Host / SNI 选择站点配置

用户无感；真正的上游地址往往只写在入口的回源配置里。

这也是安全与架构上常见的收益：源站 IP 不必直接暴露给公众。

## 5. 示例对照：Cloudflare + Netlify

下面用一套很常见的静态站组合，把抽象模型落到可操作的分工上。  
注意：它们只是示例，换成「路由 53 + S3/CloudFront」「阿里云解析 + 对象存储 HTTPS」时，分层方式同类。

### 5.1 角色如何映射

| 通用层 | 在本示例中 |
| --- | --- |
| 权威 DNS | Cloudflare DNS（假设 NS 已指向它） |
| 静态内容与部署 | Netlify Build + Hosting |
| 可选第二入口/代理 | Cloudflare 代理（橙云） |
| 用户看见的名字 | `www.example.com` |
| 平台默认调试名 | `*.netlify.app` 一类 |

部署与接入的逻辑顺序：

```text
代码推送
  → 托管平台构建并生成可访问版本
  → 在托管平台绑定自定义域（让它认这个 Host）
  → 在 DNS 服务商添加指向托管入口的记录
  → 证书在“用户到入口”的路径上签发并生效
```

两边缺一不可：

| 只做一半 | 可能结果 |
| --- | --- |
| 只改 DNS，不在托管侧绑定域名 | 流量到了平台，但平台不知道回哪个站 |
| 只在托管侧添加域名，不改 DNS | 外界仍解析到旧入口或无处可去 |

### 5.2 同为“解析到 Netlify”，橙云/灰云却是两条路

Cloudflare 记录上的代理开关，决定 Cloudflare 是否进入**数据路径**：

| 模式 | 含义 | 浏览器先连谁 |
| --- | --- | --- |
| DNS only（灰云） | 只回答 DNS | 托管平台入口（Netlify） |
| Proxied（橙云） | DNS 结果指向 Cloudflare 任播 | Cloudflare，再回源到 Netlify |

**灰云：**

```text
浏览器 →（DNS 由 Cloudflare 回答）→ 直连 Netlify → 返回站点
```

**橙云：**

```text
浏览器 → Cloudflare 边缘（TLS/WAF/缓存/规则）→ Netlify → 返回站点
```

因此：

- 灰云：Cloudflare 主要是 DNS 服务商  
- 橙云：Cloudflare 还是反向代理 / CDN 入口，Netlify 变成它的上游之一  

对个人文档站，灰云通常更好推理；若明确需要统一 WAF、多域规则、额外边缘逻辑，再考虑橙云，并认真处理 SSL 与缓存叠层。

### 5.3 证书责任随入口而变

| 路径 | 用户 TLS 主要终止于 | 还要额外关心 |
| --- | --- | --- |
| 灰云直连托管 | Netlify | 托管平台证书状态 |
| 橙云经 Cloudflare | Cloudflare | CF SSL 模式，以及 CF 到 Netlify 的回源 TLS |

这也是「同一域名，切了一下代理开关，证书签发者/排障点就变了」的原因。

### 5.4 平台 DNS 与外部 DNS

托管平台有时也提供 DNS（例如 Netlify DNS）。它解决的是：

> 要不要把**权威 DNS**也迁到托管平台，

而不是：

> 能不能绑定自定义域。

自定义域绑定 ≈ 托管层承认 Host。  
启用平台 DNS ≈ NS 搬家，全世界改去问它要解析。

域名已在别家 DNS、且还有邮箱 MX、验证 TXT、多子域多服务时，外部 DNS + 托管绑定通常更灵活。  
平台 DNS 的价值是控制台合并，不是性能魔法。

## 6. 缓存收谁控制？

缓存不是单一开关，而是沿路径分布的多层决策。

### 6.1 常见的三层

```text
浏览器缓存  →  入口/CDN 边缘缓存  →  源站/托管源
```

| 层 | 谁说了算 | 典型依据 |
| --- | --- | --- |
| 浏览器 | 浏览器 | `Cache-Control` / `Expires` / 启发式缓存 |
| CDN/代理边缘 | 入口厂商规则 + 源站头 | Edge TTL、是否尊重源站、路径规则 |
| 源站/托管 | 应用或平台默认头 | 框架/托管默认值、`_headers`、网关配置 |

任意一层“更积极”，都可能让你感觉“站点被缓存了”；  
任意一层退出，都可能让你感觉“策略突然变了”。

### 6.2 为什么切换入口后，缓存体感会变

回到示例：若之前走 Cloudflare 橙云，并在 Cloudflare 配了数小时 Edge TTL，那么：

- 真正强硬执行“边缘放一阵子”的，常常是 **Cloudflare**  
- 切到灰云后，这层退出  
- 浏览器开始更直接地面对 **Netlify 返回的响应头**

若托管默认对 HTML 更保守，例如：

```http
Cache-Control: public, max-age=0, must-revalidate
```

或：

```http
Cache-Control: no-cache
```

体感就会从“一段时间内外边直接命中”，变成“经常先问服务器变没变（可能 304）”。

这通常不是 DNS 配错，而是：

> **缓存控制权从“代理入口”回到了“托管响应头 + 浏览器”。**

### 6.3 前端静态站更稳妥的责任划分

与构建产物形态对齐：

| 资源类型 | 更合理的缓存责任 |
| --- | --- |
| HTML / 页面入口 | 短缓存或用前校验，保证发版可切换 |
| 带 content hash 的 JS/CSS | 长缓存；URL 变即新资源 |
| 无 hash 图片/ico/分享图 | 中等缓存，或改名后再拉长 |
| API / 个性化响应 | 默认不进共享长缓存 |

灰云 + 托管平台时，这些头应落在**托管侧**（如 `netlify.toml`、平台 Headers 配置）。  
橙云时，还要确认 CDN 是“尊重源站”还是“强制覆盖”，避免两套规则打架。

### 6.4 几个容易混的头（决策用）

| 写法 | 实用理解 |
| --- | --- |
| `max-age=N` | N 秒内可当新鲜的，直接用 |
| `no-cache` | 可存储，但用前先校验 |
| `no-store` | 尽量不要存供复用 |
| `public, max-age=0` | 允许共享缓存持有，但新鲜时间为 0，通常需 revalidate |
| `immutable` | 新鲜期内别无谓再验证；适合 hash 文件名 |

因此：

- 想减少 HTML 反复校验，可把页面 `max-age` 提到例如 24h，但要接受发版后部分浏览器最长短时仍见旧页  
- 想发版尽快全局可见，HTML 更适合 `no-cache` / `max-age=0, must-revalidate`  
- hash 静态资源则应尽量长缓存，不必和 HTML 同一策略

### 6.5 发版与缓存的关系

理想发版：

```text
1. 先上传/发布新的 hash 资源
2. 再切换 HTML 入口引用
3. HTML 不长缓存，或发布时让边缘 HTML 失效
```

需要分清：

- **平台边缘purge/新部署失效**：影响 CDN/托管边缘  
- **浏览器 max-age 未到期**：用户本地仍可能直接复用旧 HTML  

所以“我已经重新部署了，有人还见旧页”，不一定是 DNS 问题，更常是浏览器层还在新鲜期内。

## 7. 整条链路的责任地图

```text
[名字层] 权威 DNS
  决定：www.example.com 当前指向哪个入口名/IP
  示例：Cloudflare DNS / 其它 DNS 服务商 / 平台 DNS

[入口层] 用户 TLS/HTTP 第一跳
  决定：谁终结证书、谁先执行 WAF/边缘规则/边缘缓存
  示例：
    - 灰云：Netlify 边缘
    - 橙云：Cloudflare 边缘（再回源 Netlify）
    - 其它：CloudFront / 自建 Nginx / 对象存储绑定的 CDN

[内容层] 部署版本与源站逻辑
  决定：HTML 引用哪些资产、API 如何响应、默认响应头是什么
  示例：Netlify 某次 deploy、S3 对象、Express/Nginx 源站

[缓存层] 分布式在路径上
  浏览器 ← 入口/CDN ← 源站头与平台默认值
```

排障时按层问：

1. **名字层**：`dig` 结果是否仍是你以为的入口？TTL 是否导致旧答案？  
2. **入口层**：证书颁给谁、TLS 在哪终止、是否还有第二层代理？  
3. **内容层**：托管/源站是否绑定该 Host，当前部署是否正确？  
4. **缓存层**：响应头是什么？有没有 `age` / 厂商 cache status？304 还是 200？

## 8. 一套可复用的排查清单

### 8.1 先确认“内容本身”

- 平台默认域名（如 `*.netlify.app`）是否已是新版本  
- 若默认域都错，先别查自定义域 DNS

### 8.2 再确认“名字是否指对入口”

```bash
dig www.example.com +short
# 或 dig CNAME www.example.com +short
```

看它指向的是：

- 托管平台目标名  
- CDN 代理地址  
- 还是某台源站 IP  

### 8.3 确认“入口是否承认这个名字”

- 自定义域绑定状态  
- HTTPS 证书状态  
- www / 裸域是否只在一处做跳转  

### 8.4 确认“缓存听谁的”

浏览器 DevTools → Network：

- `cache-control`  
- 是否 `304`  
- 是否存在 `cf-cache-status`、`x-cache`、`age` 等  
- HTML 与 `/assets/hash.js` 是否策略分离  

无痕窗口、禁用缓存、对比默认域与自定义域，能快速判断问题在 DNS、入口还是本地缓存。

## 9. 静态站场景下更稳妥的默认答案

若你的目标是个人站/文档站/前端静态资源托管，而不是复杂边缘计算，一个不容易把自己绕进去的默认是：

1. **权威 DNS 放在通用 DNS 服务商**（可继续用 Cloudflare DNS）  
2. **内容托管放在静态平台**（如 Netlify / Pages / 对象存储+CDN）  
3. **DNS 记录仅解析，不轻易叠第二层代理**（对应 CF 灰云这类模式）  
4. **自定义域在托管侧绑定，证书以用户实际入口为准**  
5. **缓存头在内容出口明确写出**：HTML 短/中，hash 资源长  
6. **跳转、HTTPS 强制、SPA rewrite 尽量只在一处配置**

它换来的不是最多功能，而是最好推理：

```text
名字怎么解析？ → DNS 服务商
页面从哪出？   → 托管/源站当前部署
第一跳是谁？   → 解析目标（若无额外代理，就是托管边缘）
缓存听谁的？   → 主要听内容出口的 Cache-Control
                 （若有代理层，再加上代理规则）
```

## 10. 总结

1. **DNS 负责名字到入口的映射，不负责直接“存放网页文件”。**  
2. **浏览器先连的是入口，不一定是最终内容生产者。**  
3. **URL 中的域名可保持稳定；背后入口与回源可以替换。**  
4. **缓存是多层的：浏览器、CDN/代理、源站头，切换入口等于切换缓存治理者。**  
5. **Cloudflare + Netlify 只是一种常见分工示例**：前者常作 DNS（可选代理），后者常作静态部署与内容出口。  
6. 遇到异常时，按 **名字层 → 入口层 → 内容层 → 缓存层** 排查，比混成一句“域名有问题”有效得多。

一句话：

> 域名是门牌，DNS 是路标，入口是前台，源站/托管是仓库；缓存则是沿途可能设立的货架。  
> 弄清每一层由谁掌管，才能正确理解“解析、访问与刷新”到底发生了什么。
